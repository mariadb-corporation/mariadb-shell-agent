# MariaDB Code

MariaDB Code is a fork of [Qwen Code](https://github.com/QwenLM/qwen-code) with MariaDB branding,
including the VS Code extension (used in local VS Code and in `../mariadb-cloud-ide`). It follows
upstream closely: the fork is rebased onto upstream as soon as upstream moves.

## What differs from upstream

| Area                                | MariaDB Code                                                                        | Upstream                                                 |
| ----------------------------------- | ----------------------------------------------------------------------------------- | -------------------------------------------------------- |
| Name, icons, banner, Web Shell logo | MariaDB Code, MariaDB seal                                                          | Qwen Code                                                |
| CLI command                         | `mariadb-code`, short `mdbc`                                                        | `qwen`                                                   |
| Config directory                    | `~/.mariadb-code`, `<project>/.mariadb-code`                                        | `.qwen`                                                  |
| Project instructions                | `MARIADB-CODE.md` (`AGENTS.md` is read too)                                         | `QWEN.md`                                                |
| Ignore file                         | `.mariadb-codeignore`                                                               | `.qwenignore`                                            |
| Environment                         | `MARIADB_CODE_<X>` overrides `QWEN_<X>` / `QWEN_CODE_<X>`                           | `QWEN_*` only                                            |
| VS Code extension                   | `MariaDB.mariadb-code`, commands and settings `mariadb-code.*`                      | `qwenlm.qwen-code-vscode-ide-companion`, `qwen-code.*`   |
| Model providers offered             | DeepSeek, Grok, MiniMax, Z.AI, Kimi, OpenRouter, Requesty, custom OpenAI-compatible | also QwenCloud, Alibaba ModelStudio, Idealab, ModelScope |
| Alibaba endpoints                   | none: every Alibaba and QwenLM host is made unresolvable (`.invalid`)               | self-update, telemetry, Qwen OAuth, …                    |
| Usage statistics, self-update       | off by default, and nowhere to send to or download from                             | on                                                       |

Not renamed: the `QWEN_*` variable names themselves (169 of them; use the `MARIADB_CODE_*`
aliases), internal file names inside the config directory, `qwen-extension.json` (the extension
manifest format), and Qwen model names.

The Alibaba presets stay registered internally (reasoning overrides and the extension's plan
definitions look them up), but no picker or provider list offers them and their hosts do not
resolve.

Not touched, because they are identifiers rather than endpoints: the JSON-schema `$id`s of the
managed-runtime contracts and the Kubernetes CSI driver name `diskplugin.csi.alibabacloud.com`
(see `mariadb/leak-allowlist.json`).

Features that only worked against Alibaba or QwenLM services are gone with their hosts: the
standalone self-updater and installers, the Live host and managed-runtime downloads, Qwen OAuth,
the OSS artifact publisher, and the QwenLM sandbox image (`config.sandboxImageUri`; a sandbox
needs an image of our own).

## How the fork is kept rebase-friendly

Upstream files are never edited by hand. `main` is upstream plus two kinds of commits:

```
upstream/main (or an older upstream commit, see --to)
  <- fork commits: everything under mariadb/
  <- "MariaDB branding (generated by mariadb/rebrand.mjs)"
```

- `mariadb/rebrand.mjs` runs the rules in `mariadb/rebrand/`, one module per topic (identity,
  product name, artwork, alibaba, paths, cli-name, extension-ids, review, skipped-tests). Each
  rule fails loudly when upstream moves its anchor.
- `mariadb/rebrand/skipped-tests.mjs` lists the upstream tests of behaviour we removed (update
  checks, usage statistics defaults, Alibaba providers in pickers, QwenLM endpoints), each group
  with its reason. A test that fails because a rule renamed something inconsistently is a rule
  bug, not an entry there.
- The generated commit is thrown away and recreated on every sync, so it never conflicts.
- Fork commits only touch `mariadb/`, which upstream does not have, so they never conflict either.
- `mariadb/check-leaks.mjs` scans the branded source (and with paths, build output such as a
  `.vsix`) for old names and Alibaba hosts. Known, intended exceptions are listed with a reason
  in `mariadb/leak-allowlist.json`.
- `mariadb/verify.mjs` runs the unit tests of the touched packages, reruns failing files in
  isolation and then against the pristine upstream sources, and reports only the failures the
  branding causes.

| Remote     | URL                                             | Use                        |

| `NAS`      | `https://github.com/mariadb-corporation/mariadb-shell-agent` | our fork; `main` tracks it |

## Sync with upstream

```sh
mariadb/sync-upstream.sh                    # fetch, rebase, regenerate branding, install, leak scan
mariadb/sync-upstream.sh --verify --push    # ... plus the test gate (~1 h), then force-push to NAS
mariadb/sync-upstream.sh --to <rev>         # rebase onto an older upstream commit (upstream main broken)
```

The script also works when upstream has nothing new; run it after committing a change to
`mariadb/` to regenerate the branding commit. `--push` only happens when the leak scan (and with
`--verify`, the test gate) passed.

If a rule stops with "anchor not found", upstream changed that spot: discard the partial branding
(`git reset --hard HEAD && git clean -fd -- . ':!mariadb'`), adapt the rule in
`mariadb/rebrand/`, commit it (`git commit -- mariadb/`) and run the sync again. The same applies
when the leak scan finds a new occurrence: extend a rule, or allowlist it with a reason.

## Build the VS Code extension

```sh
corepack pnpm install --frozen-lockfile
mariadb/build-vsix.sh             # this machine, e.g. mariadb/dist/mariadb-code-<v>-darwin-arm64.vsix
mariadb/build-vsix.sh universal   # any platform, no node-pty: for the MariaDB Cloud IDE (Pi, arm64)
code --install-extension mariadb/dist/mariadb-code-<v>-darwin-arm64.vsix
```

Each build is leak-scanned after packaging. In `../mariadb-cloud-ide`: `npm run
plugin:mariadb-code` unpacks the newest universal build into `plugins/`, then `npm run deploy:pi`.
